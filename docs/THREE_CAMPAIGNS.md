### A — Camera + IMU / EuRoC external published baseline

The cloud uses the pinned upstream OpenVINS commit
69488123ed9362dd44b6f28e7f4680abbff1442b,
ov_eval/example/stamped_groundtruth.txt and stamped_traj_estimate.txt.
The OpenVINS upstream README labels the estimate as VINS-Mono on
EuRoC MH_01. We download both **actual published recorded trajectories**,
hash them and evaluate them with our previously implemented independent
benchmark tool with SE(3) rigid alignment, no hidden scale fitting.

Result of GitHub Actions run 39158822466 (external VINS-Mono baseline):
- 3,638 timestamp pairs; 181.905 s independent reference span.
- ATE translation RMSE: 0.2040944 m.
- Relative 1 s translation RPE RMSE: 0.0275042 m.
- Relative 1 s orientation RPE RMSE: 0.2063174 degrees.
- Evaluated reference path: 79.9660 m; estimated: 79.1402 m.
- Estimated path error on matched, contiguous samples: -1.0327%.
- Time-coverage fraction over available truth: 99.9698%.

**NOT A SCORE OF OUR ANDROID APPLICATION.** We did NOT reconstruct
camera images or IMU values with OpenVINS; the estimator trajectory was
already produced and distributed in an external reference repository.
The precise camera-vs-body reference-frame alignment must be verified
before using orientation/translation values for publication-grade claims.
This is the first real-data test of our *evaluator*, not our estimator.

### B — IMU only, entirely without camera

We have an actual executable reference *fixed-stride PDR estimator*:
tools/campaigns/imu_pdr.py. It consumes only timestamped accelerometer and
gyro measurements (optional magnetometer/barometer are indexed, not fused)
and outputs a metrically prior-scaled trajectory TUM file. The algorithm:
- threshold-step detection on acceleration magnitude after smoothing;
- integrates angular rate along explicitly selected assumed heading axis;
- uses configurable fixed step length, threshold and gyro bias;
- holds position when stationary and avoids joining large sensor gaps.

GitHub Actions run 39158822466 executed an artificial 15 s inertial trace
with no video input, detecting 24 steps; smoke tests also cover stationarity
and turns. These **cannot quantify real human pedestrian accuracy**.
Fixed stride is not suitable for varying gait, arbitrary phone rotations
or long-term yaw stability; real RoNIN, OxIOD, RIDI evaluations are needed.

OxIOD synchronized CSV import is implemented by tools/campaigns/oxiod.py;
uses gyro columns 4:7, gravity 7:10, user acceleration 10:13 in original
array order. It reconstructs gravity-inclusive acceleration in m/s2 and
can export the reference pose as a separately labeled *optical* or
*visual-inertial proxy* reference. Verify the per-version OxIOD CSV time and
axes before running real recordings. Neither the importer nor PDR has
yet been evaluated against an actual downloaded OxIOD user trajectory here.

    python tools/campaigns/run_dataset.py \
      --campaign B --kind oxiod \
      --input '/data/oxiod/handheld/data4/syn/imu1.csv' \
      --out campaign_results/b_real_pdr

Use --kind canonical --input PATH for a 5-column t_ns,type,x,y,z
log already generated by our generic adapter. This permits recorded
phone Camera2/IMU or custom RoNIN/RIDI sensors after conversion.

Ground-truth scoring requires a declared quality class and consistent
clock, camera/body extrinsics and pose origin; an arbitrary first-step
direction is NOT reference-aligned heading. We do not silently score
unknown device/reference frames as true metric 6DoF.

### C — Real phone / ARCore dataset replay

Implemented in the EXISTING MainActivity, not an independent simplified
viewer. DATA > ARCORE REPLAY provides recorded session video selection and
file-document import. External document MP4s are copied into private phone
storage to guarantee a *seekable* file. Plain video MP4 is rejected by
ARCore (only official ARCore Recording API sensor dataset MP4 is valid).

Replay starts a clean MainActivity / Session:
- configure camera session as normal, setPlaybackDatasetUri **before** resume;
- feed ARCore Frames through exactly the existing processFrame logic,
  AnchoredOdometry, Odometer, CSV recording, real SceneMapper and HUD;
- log PLAYBACK_SOURCE, PLAYBACK_END_FRAMES_N_TRACKED_M in exported CSV;
- do not log current-device IMU or GPS as if it belonged to past video;
- end cleanly after PlaybackStatus.FINISHED, allowing CSV export;
- after Activity background pause, restart replay to avoid implying
  dropped source video frames were replayed.

The APK compiled with Android unit tests / lint on GitHub Actions run
39158822466, with the artifact named campaign-c-arcore-replay-apk.
The code is an on-device experimental replay UI and **has not yet been
physically launched on a Galaxy S21**; live ARCore performance remains
device-dependent. Pose repeatability on the same MP4 is itself not guaranteed
by ARCore. No claim of metric accuracy without surveyed ground truth.

To perform a field campaign:
1. Install the CI-generated APK (Android app may need uninstall if signing
   changed; back up sessions/maps before uninstall).
2. DATA > Training video > ARM CAPTURE, then START.
3. Record controlled loops/stationary/walking/running routes, export ZIP.
4. DATA > ARCORE REPLAY, select same internally saved MP4 or import the
   recorded ARCore MP4; play from start to FINISHED; export CSV.
5. Run plot_session.py or tools/campaigns/run_dataset.py with independently
   measured total route length. Compare repeat passes, gaps, coverage,
   smoothness, FPS, thermal and battery separately.

For a previously exported VECTOR CSV, hosted cloud/local runner:

    python tools/campaigns/run_dataset.py \
      --campaign C --kind phone_csv \
      --input '/data/phone_s21/vector_vio_20261018_XXXXXX_000.csv' \
      --known-distance 10.0 \
      --out campaign_results/c_phone_field

Only the known independent measured *path length* certifies distance
error; it does not make an ARCore pose a ground-truth 6DoF trajectory.

The optional GitHub manual workflow drive-campaigns.yml requires secret
SLAM_RCLONE_CONFIG_B64 with a base64-encoded rclone config containing a

connector's authenticated session is NOT automatically available to
GitHub Actions. Make a dedicated limited-scope Drive OAuth credential;
store only via GitHub repository Actions secrets, NEVER commit it.

Once workflow is present in the repository DEFAULT BRANCH and the user
has set that secret, trigger workflow_dispatch with campaign, kind,
dataset_path (under SLAM_BENCHMARKS/01_RAW), input_file if B/C and
estimate_file if A. Script copies one dataset folder into ephemeral
GitHub workspace; results go back to private Drive 04_REPORTS. Raw phone
files are never uploaded as public workflow artifacts. The job retains
only minimal status.json as an artifact.

**Run limitations:** GitHub's hosted runner must have enough available
disk, processing time and network allowance. Very large sequences and
heavy OpenVINS/ORB-SLAM3 builds belong on a self-hosted Linux/Windows
runner. Even when this data pipeline is ready, the live ARCore estimator
cannot execute in the GitHub-hosted Linux container, because the ARCore
Android runtime requires supported device environment.
